# AI 销售策略运行合同

- status: active-production-observation
- owner: reply-runtime
- source_of_truth: `ai_paths/app/policies/ai_sales_policy_v2.json`、`ai_closing_catalog_v1.json`、外部 Follow Knowledge 已发布目录与当前 V3 代码

## 边界

- V3 Reply 是唯一销售语义决策点；不另建意图、卡点或逼单决策链。
- 策略配置描述场景、节点目标、节奏和素材来源；模型决定是否采用，代码只校验稳定 key、权威事实、交易边界和发送结果。
- 话术只作改写参考。每次回复最多采用一个解题方向和一个合法销售动作。
- 图片和视频只能来自本轮检索后保留的候选 URL；不得编造素材、门店、订单、活动或支付事实。

## 统一决策合同

- 启用策略时，V3 Reply 在同一次模型调用中输出 `policy_decision`；不得为意图、情绪或逼单再建立独立客户语义决策服务。
- `realtime_intent.type` 是本轮最终主意图，`secondary_types` 只保留其他有效信号；Semantic Router 的意图字段只用于检索与工具规划。
- `emotion_decision.label` 描述客户发送本轮消息时的情绪，只能调整表达压力和流程动作，不能授权交易或事实承诺。
- `closing_decision` 只允许 `none|enter|advance|pause|fallback|complete`；客户新消息必须重新判断，新卡点、暂缓、明确退订和暂停营销情绪不得机械推进旧节点。
- 策略配置固定管理 7 类实时意图、8 类情绪、任务优先级、安全边界和 Shadow 模式；逼单规则、策略和节点不再复制进本地 policy。
- policy 加载时必须校验决策 schema 版本、7/8 完整目录、情绪流程动作枚举、`catalog_source=configured_closing_catalog` 和 `silent_tasks_mode=off|shadow`；本轮目录可按配置来自外部接口或版本化本地 JSON，但规则、策略、节点和话术必须同源，配置不合法时不得静默启用。
- 主任务、主意图、情绪流程动作、逼单动作和客户状态属于运行必需字段。它们缺失、非法或与同轮客户动作自相矛盾时，只允许使用 Reply 既有的唯一一次修复机会；修复仍失败时返回非营销安全收尾并标记 `decision_status=degraded`，不得让客户请求失败。
- 置信度、次要意图、说明和补充证据属于 BI 观测字段；缺失时只降级记账，不触发第二次模型调用。
- 首次输出中有客户证据且被代码核实的明确退订、人工接管、关系删除、医疗高风险或具体严重客诉/退款纠纷构成本轮修复的安全下限；修复不得将其改成普通聊天或直接推进。模型单独给出的情绪标签、普通质疑、讲价、软拒绝和单句粗口不构成永久停止营销事实。
- `cardpoint_decision.state=active|repeated` 时必须先解卡并暂停逼单；只有 `resolved` 才允许重新判断是否进入或推进序列。
- `closing_decision.action=pause` 可以表示“当前不进入逼单”，尚未开始任何序列时 `sequence_key=none`、`node_key` 为空是合法状态，不得按缺失序列判为结构错误。
- `closing_decision.action=none` 只表示本轮不进入逼单序列，不表示正常销售主线停止。无活动卡点且交易未终态时，Reply 回答当前问题或完成本轮信息交付后仍应选择一个与阶段匹配的主线动作；客户提交上一轮要求的门店、时间等信息时，Router 可用 `current_intent.continuation_signals` 保留 `information_submission`/`transaction_progress` 证据，但最终动作仍只由 Reply 决定。
- 正常销售轮次的客户可见文字最多包含一个问题；Reply 声明 `action=ask` 时必须实际包含该问题。代码只检查问号数量和结构声明是否落实，不通过中文关键词推断客户意图或替模型选择销售动作。
- 活动卡点下 `sales_judgment.posture=switch` 表示从逼单切换到解卡路径，可以采用跟进序列或卡点话术；它不等于 `closing_decision=advance`。如果模型误把该观察标签写成 `advance`，但最终 closing 已暂停、客户可见动作和结构消息均安全，不能仅凭标签丢弃整段解卡回复；明确退订或暂停营销时仍禁止 `switch/advance`。

## Prompt 治理

- Router 中的信任、效果、暂缓和退订例句只校准完整语义边界，不是字符串命中规则；Router 输出是召回证据，不能锚定或替代 Reply 的最终意图、情绪和逼单判断。
- Reply Prompt 按硬边界、当前任务、本轮销售目标、候选证据、表达与输出合同分层。相同原则只保留一个权威表述；`flow_action`、业务名称和 `decision_status` 等可由目录或代码确定的字段不要求模型生成。
- 完全没有可解析 Reply JSON 时，唯一一次 full retry 重新执行原任务；已有 JSON 时只允许 targeted repair 修结构、真实 ID 或事实冲突，必须保留未冲突的销售判断，不得成为第二个销售大脑。
- Prompt 精简属于回复质量改动。合入前必须通过确定性边界测试和 DeepSeek 同样本对照；回复通过率、安全指标、序列/话术条件采用和延迟任一明显退化时回退该次精简，而不是继续追加例外规则。
- 客户可见表达先回答当前问题，再落实一个相关下一步。业务层不固定一条或两条：答题、证明和推进可以拆成多条各自独立成立的自然微信，单条文字目标 20～60 字；发送端以每轮最多 8 条客户可见消息、文字合计最多 300 字作为异常保护，而不是销售创作目标。不得硬切完整句子、输出内部审计口径、客服菜单或同义重复；超限时只做一次格式压缩，不重新判断销售策略。普通销售轮整轮最多一个轻表情，投诉、退款、医疗风险和付款核验不用表情。当前消息高于不可靠旧历史，历史冲突、测试噪声或未真实交付草稿不得恢复旧门店、旧活动或旧订单话题。
- 本轮已具备且允许直接交付的价值不得再经过“要不要看/要不要发”的许可式空转：权威活动价直接回答；效果、信任或以效果价值解其他卡点时，若存在直接相关、未重复且无冲突的真实图片/案例，Reply 应用一句短文字引出并在同轮选择素材 ID 交付。只有 `hard_stop_marketing`、明确退订、人工接管、关系删除、医疗高风险、具体严重客诉/退款纠纷、素材无关或已发送时不得强发；模型单独给出的情绪标签或普通软拒绝不能拦截客户明确索要的价值。
- 跟进话术的文字采用与媒体交付分开记录：`knowledge_use.script_id` 说明采用了哪条表达，`selected_content_ids` 记录本轮真实结构媒体。带媒体的话术必须同时出现在“可直接交付素材”目录中；文本话术或已去重媒体不得伪装成可发送内容 ID。Reply 已选择真实 `script_id`、该话术存在当前安全可用且未发送的配套媒体、但漏填重复的 `selected_content_ids` 时，代码只按同一话术 ID 补齐最精简媒体组；不得跨话术、跨卡点或在 `hard_stop_marketing`、明确退订、人工接管、关系删除或安全风险场景补发。
- 首次询价可以解释有权威事实支持的预约金抵扣、退款等机制，但不得因此主动发送付款卡；只有客户进一步表达报名、预约或付款意向，并满足真实订单与交易边界后才允许发卡。
- 客户询问具体广告或案例真实性时，只有本轮权威案例事实可以支持确认；目录话术、历史泛案例和模型常识均不能证明“该广告/该人物案例是真的”。
- 最终 Reply、full retry 和 targeted repair 使用同一 DeepSeek Reply tier；该 tier 不继承全局 GPT emergency fallback。DeepSeek 不可用时返回既有中性安全失败回复，不能静默切换其他供应商。

## 销售状态与主线恢复

- Reply 必须把客户状态归一为四类：`continue_sales` 表示正常沟通和普通软拒绝；`pause_current_turn` 表示本轮降压但不结束后续销售；`hard_stop_marketing` 表示合同明确的硬停止；`post_payment_service` 只由平台权威已付事实触发。
- 每个正常销售轮必须选择并在客户可见消息或结构消息中落实一个 `next_sales_action`：交付效果案例、介绍活动、询问卡点/城市、发送门店卡、解释预约金、发送真实收款卡、收集到店偏好或进入付款后服务。它不是 BI 记账口号，不能只写在结构字段里而没有实际动作。
- 当前问题永远先回答，随后依据真实已送达记录恢复最早缺失主线：需求 → 效果/项目 → 活动价值与价格 → 门店 → 预约意愿 → 预约金。客户可以跳问，系统也应直接回答，但回答后的推进不能因为混乱旧历史跳过尚未交付的关键价值。
- 一轮只推进一个方向，不同时堆门店、到店时间、名额和预约金；不强制用问号收尾，直接交付素材、门店卡或付款卡本身就是有效推进。

## 素材、话术与价格事实

- 效果、信任或使用效果证据解卡时，只要本轮有相关、未发送且无事实冲突的真实素材，必须同轮按“短文字 → 图片/视频”交付一个最相关素材组，不得先问“要不要看”。客户明确要求多看时可以选择 2～3 个视觉不同的案例组，仍受 8 条/300 字异常保护。
- 素材去重不能只看 URL；运行时同时使用文件 SHA-256 与感知指纹识别同图换 URL，并结合相关性、卡点、部位/人群、近期使用和表达多样性排序。无法取得内容指纹时保留 URL/稳定 ID 去重作为降级，不能把指纹失败解释为可重复轰炸。
- 话术排序应惩罚近期已用 `script_id`、相同论据和高相似文本，避免持续选择目录第一条；卡点类型仍是硬边界，动作和 tag 是软排序。目标是安全候选的高条件采用率，不是把不相关或冲突内容强制用到 100%。
- 268 元只对应面部斑点改善这个部位：两侧脸颊按实际斑点位置处理，不按左右拆成两个价格，也不得表述为对无斑区域进行无差别“全脸操作”。脸部与手部属于两个部位，不能合计只收一个 268；二次或后续价格不得自动沿用 268，只能以届时有效活动和门店确认结果为准。
- 首次只问价格时直接说明权威活动价、包含价值和已有事实支持的预约金机制，但不发送收款卡；客户后续明确报名、预约、怎么付或索要入口，且订单、金额和付款结构齐全时，同轮直接发送真实收款卡，不再询问是否需要。
- 价格窄范围事实校验只修正或拒绝冲突表达，不重新选择销售策略；业务仍负责从外部话术/素材目录删除错误项目和过期内容，并提供可核验的版本或 checksum。

## 门店信息与到店服务边界

- 门店工具得到唯一真实 `delivery_store_id` 时，同轮必须交付自然说明和对应 `store_address` 卡；厦门唯一店等明确单店场景不得再问“要不要发地址”。多店、位置不足、无匹配、重复索要地址与已发卡详情查询继续按门店事实合同处理。
- 公开门店地址可以在付款前发送；楼层、房间、门面号、接待方式和详细导航属于到店指引，只有平台权威确认预约金已付且门店已确定后才可交付。客户口头说已付必须先核验付款方式、凭证或平台记录，不能直接进入已付服务。
- 门店没有权威营业时间时不得输出任何具体时段。客户追问时应如实说明该信息尚未同步，并记录结构化 `store_fact_followup` 待补事实；该记录用于运行审计和后续处理依据，不得伪装成已经创建或送达的外部人工工单。
- 技术故障使用中性失败回复；只有显式启用且独立验收通过时才进入客户可见恢复。营业时间、到店指引等业务事实缺失不走技术兜底，仍需给客户一个不承诺可接待的说明，并在事实允许范围内继续一个合法销售动作。

## 业务逼单目录

```text
租户逼单规则 + 启用策略（外部接口或版本化本地 JSON，只读、缓存）
  → Semantic Router 在唯一一次调用中识别卡点、工具需求并召回规则/策略条件
  → 代码从同一来源目录稳定排序：最多 3 条普通序列、合计 4 个当前节点；普通话术按当前卡点类型一次取池后裁剪为最多 6 个段落
  → 必要门店事实工具补齐；不再进行 post-store 销售语义重算
  → 按逼单节点话术类型严格查询同来源话术
  → V3 Reply 在唯一一次最终调用中选择规则、策略、节点、话术与回复
  → 代码校验来源 ID、证据、前置项、禁忌、限频、节点时机和话术类型
  → 即时回复；延时节点只写 shadow
```

- 规则回答“当前业务场景是否具备逼单资格”，策略回答“可采用哪套节奏”，节点话术类型回答“从哪类已发布表达中取材”；三者都不是客户可见动作命令。
- Router 只做高召回候选。规则命中必须引用本轮真实客户消息；Reply 采用目录策略时必须输出 `trigger=business_rule`、本轮目录中的 rule/sequence/node 稳定 ID，并仍是唯一最终语义决策者。
- 普通跟进序列与卡点话术采用双轨候选：序列节点动作解释策略节奏，话术解决当前客户卡点，二者互相提供排序证据但不再互相卡死。普通话术只以第三方 `checkpoint_type_id` 作为硬边界；本轮 tag、Router 表达焦点和序列节点 action 作为排序加分，不作为过滤条件。查询同类型已发布内容后执行文本相关度排序、重复内容去除和总字符预算；Top-6 内同一动作或标签最多保留 3 个不同版本，既给准确场景保留改写余地，又避免单一卡点整库灌入，且不得跨卡点类型补齐。
- 同类型目录确实有已发布话术时，动作或标签错位不得再导致候选为零；同类型目录为空、接口不可用或所有内容均不合法时必须如实记录为空，不得伪造知识候选。逼单话术继续严格匹配节点 `followCheckpointTypeId`，不参与普通话术的同类型自适应召回。
- 确定性排序不是业务结论。最终 Reply 必须复核客户当前原话、权威事实和允许的推进压力，并可独立采用普通跟进序列和同卡点话术。活跃或重复卡点已有直接相关、无事实冲突且符合当前沟通许可的话术时，Reply 必须采用其中一个主话术并记录真实 `script_id`；允许只改写其中安全的一到两句。候选不相关、压力不合适或全部存在事实冲突时可以不采用，但必须记录真实原因，不能为了采用率强用。只有话术动作与真实序列节点动作一致时才写入 `sequence_links`；同类型语义候选不得伪装成节点直属话术。
- 最终选择“效果案例”作为解卡方式且同一候选存在可发送媒体时，默认直接交付证据，不得只改写文字后反问客户是否想看效果。一次只选择一个最相关内容组；能够用单张图片说明时优先单图候选，避免为了采用率堆叠图片、视频或多组素材。
- 客户直接询问可改善的斑点/效果范围，或 Reply 决定用效果价值解卡时，只要本轮存在相关、未重复且无事实冲突的可发送效果素材，就必须在回答文字后同轮交付一个素材；不得只口头说“可以发”或再次征求许可。
- “没时间、在忙、晚点、考虑一下、有空看看、不用了、太贵了、骗子吧”、普通讲价、一般质疑和单句粗口都不单独构成退出。Reply 先回答或低压承接，再交付一个无需客户立即回复的相关价值；原因明确时使用对应卡点话术，原因未知的“考虑一下”只追问一次真实顾虑。客户明确正在开车、工作且要求稍后再聊时只暂停当前轮，后续仍可进入合法唤醒。只有明确停止联系、人工接管、关系删除、医疗高风险、具体描述我方服务损害/退款纠纷/骚扰或监管投诉时停止 AI 营销；权威预约金已付则转入预约和到店服务，不继续重复销售。
- “我先帮您留着/保留活动名额”属于允许的销售承接，不作为系统已登记或预约完成事实拦截；它不得被记账为真实预约、排客或登记终态，也不得升级成“已经预约成功/登记完成/排客完成”。真实交易终态仍只由权威订单、预约或提交结果确认。
- Router 识别到当前卡点时，Reply 只有明确把同一轮卡点判为 `resolved` 才能推进；否则代码保守暂停。这是证据一致性校验，不把 Router 变成最终销售决策点。
- 节点话术类型 ID 是同一目录内的话术类型外键。外部目录使用 `followCheckpointTypeId`，本地目录使用保留的本地类型 ID；检索返回的类型必须一致。若 Reply 采用话术，话术必须与最终 sequence/node/type 关联。没有真实话术候选时允许 Reply 自行组织低风险表达，但不得伪造知识库内容。
- `delay>0` 的节点只能作为 `silent_after` shadow。`delay=0` 但 timing 不是明确“进入逼单后/立即”的自由文本节点视为 event-driven，不得冒充本轮即时动作。
- `maxPerDay` 与 `minIntervalMinutes` 首版按同一销售接触边界内 Reply 已作出的 `enter|advance|fallback` 决策保守计数；它限制销售压力，不等同于送达次数。真实触达和送达转化仍按 dispatch/delivery 字段单独统计。
- 上游 `taboos` 当前混合客户阻断条件和回复行为禁令。Reply 只把本轮真实发生的客户状态写入 `blocking_taboo_ids` 并暂停；“不得承诺/不得虚构”等文本直接约束表达，不伪装成客户状态。
- 当前临时目录由 `AI_CLOSING_CATALOG_SOURCE` 选择：`external` 不回退，`local` 不访问逼单接口，`external_then_local` 只在接口未配置、异常或返回空目录时切换到版本化本地 JSON。两种来源不会在同一轮混用，来源和 checksum 必须保留。除该显式配置外，不得再使用 policy 内的演示序列或其他隐式策略顶替。
- 当前版本化本地目录来自业务《逼单规则策略话术业务收集_真人成交版》：9 条规则、16 套策略、37 个节点类型、42 条话术，状态仍为 `provisional`。业务正式导入第三方接口后继续使用 `external_then_local`，外部规则和策略正常且非空时自动切换为外部权威目录，无需新增代码分支。
- “预约金有效期/退款、不愿先付、支付操作受阻”等目录项是 B 单过程中的解卡或支付协助候选，不代表可以立即推进。Router 可以召回其策略和话术；Reply 在问题未解决、支付风险未核验或客户未接受解释前必须 `pause`，但允许在 `knowledge_use` 记录实际采用的解卡序列和话术。
- 本地话术中的预约金金额、有效期、退款/抵扣、门店、交通、可用时段、多人金额和支付入口均标记权威事实要求。目录只证明业务推荐表达，不证明这些动态事实当前成立；缺少对应事实时不得照抄。
- 目录缓存陈旧时允许使用 last-known-good，并在 BI 写 `closing_catalog_status=stale`；进程重启后的首轮仍需重新读取。当前服务实例只有一个知识租户，所有 `slXXXX` 企微号共享同一个只读知识凭证与知识缓存；客户状态仍按销售接触边界隔离。
- 若未来新增第二个业务知识租户，优先部署独立服务实例和 token；当前不以 `corp_id` 猜测知识租户，也不预建闲置的 token 路由。
- 门店城市/区域查询可保留完整已授权候选用于事实审计：不超过 6 家且没有重复交付时可全部交付门店卡。城市级候选超过 6 家且客户只确认是否有店时，先告知真实覆盖区县并追问客户所在区县或附近地标；只有客户明确要求全部/所有门店清单时，才按编号逐行输出完整“门店名 + 区县 + 地址”文字清单。同一城市的明确全量列表中只要包含已送达门店卡，本轮仍改用完整文字清单，不能通过删掉已送达门店后把全量清单说少。事实生成、Reply 合同与失败恢复必须共同引用同一组 `delivery_store_ids` 或同一份完整文字候选，不能各环节使用不同范围。
- 门店历史必须分别保留 `latest_delivery` 与 `latest_recommendation`：前者用于结构消息幂等，后者保留真正的位置/区域匹配依据。停车、营业时间、楼层等已知门店详情查询不得覆盖原推荐的查询城市、区县、精度、是否完成、是否允许继续细化、排序方法和推荐门店 ID。
- 客户已收到当前城市的最终门店推荐后表达距离卡点，若没有提供新城市，不再追问同城地铁站、路口、楼栋或更细地址，不重新查询或重复发送门店卡；必须先用可用的距离卡点序列和安全话术处理顾虑。第一句只用“那没关系呀/没事的”轻承接，随后客户可见文字不得再用“距离、远、折腾、麻烦”复述顾虑，即使候选原文有也不能照搬；立即把注意力转向技术、效果、案例和是否值得，正向社会证明可以说“专程过来/花一两个小时过来”。客户仍明确拒绝该城市门店时，才询问是否有其他方便前往的城市；提供新城市后才重新匹配。没有公里数或路线排序事实时不得客观断言门店确实远或近。行政范围匹配只能说明“当前范围匹配到这家”，不得伪装为全城数学最近。
- 客户已收到并确认某家门店后，再问停车、营业时间、楼层等非地址详情时不得重复同一门店卡、完整地址或道路信息。若客户尚未预约、没有新卡点/暂缓/投诉/健康风险，答清详情后应明确把时间偏好连接到预约登记；可以说明本轮权威事实支持的 10 元预约金锁活动名额，但不得声称已预约、已保留免费名额或主动发送付款卡。客户明确再次索要地址或导航时允许重发门店卡。
- 客户响应上一轮选择门店的提问并提交具体门店时，Reply 必须先交付真实门店事实；回答后的推进按真实交付状态决定。效果/项目或活动价值尚未交付时先补最缺的一项，不得直接跳问到店日期；效果、活动和门店都已可靠交付且客户仍有行动条件时，才询问一个到店日期或时段。任何阶段都不得在同一轮同时要求留名额、支付预约金和确认到店。

## 回复返回与可靠收尾

- 同一平台消息由持久 `generation_key` 绑定唯一 run、稳定 `response_id` 和逐条稳定 `client_message_id`；数据库重放只复用原结果，不得再次运行销售模型。AI 服务内部幂等与聚合平台是否重复发送必须分别统计。
- 客户可见回复、助手消息和运行核心终态必须在 HTTP 返回前一次事务落库；完整节点轨迹、BI、客户画像观察、知识采用、Shadow 和策略回写通过 `runs.output_snapshot.post_reply_finalization` 形成持久、幂等的待收尾状态，由 Worker 异步补齐。
- 收尾状态必须支持进程重启恢复、短暂失败退避重试和重复执行幂等；不得使用仅存在于进程内的临时后台任务。收尾失败不撤销已经生成的客户回复，也不得把正常业务请求改成空回复。
- 客户可见恢复默认关闭。本次发布保持 `V3_REPLY_RECOVERY_ENABLED=false`；后续独立启用时，只有正常销售链因技术异常只能返回“您稍等一下”的原 run 才可标记为 `fallback_pending`。恢复 Worker 最多两次生成，并在发送前复核最新客户消息、AI/人工状态、退订/删除、交易终态和既有送达；成功补答使用固定 `v3-recovery:<original_request_id>` 幂等键，失败转人工待复核，不允许无限自动发送。
- 同步生成所有权与客户可见自动补答是两类机制：即使自动补答关闭，相同平台消息的后续请求也可以原子接管“仍为 generating、显式租约已过期、没有持久结果且没有 dispatch”的原 run，并沿正常同步链生成结果；必须复用原 `request_id/response_id`，竞争失败只允许等待或重放，禁止产生第二结果或主动发送。
- 管理日志必须分别展示完整 HTTP 耗时、模型/工具节点耗时和收尾状态；待收尾期间不得把未记录的 BI 或候选字段显示成业务零值。
- 预约与到店时间是默认可协调的业务能力：正常销售轮次可以主动询问客户方便的日期或时段；客户给出具体时间后可以确认“该时间可以协调”并先记录为到店意向。该能力不证明具体空位、已确认档期、门店事实或预约完成；没有相应权威事实时，仍不得声称已有空位、已经预约/登记/安排/留位、准时等候或可以直接到店。门店未确定时可以收集时间意向，但不得猜测门店、地址或区域。

## 跨轮与归因

- 上一轮只向 Reply 提供同一销售接触边界内的稳定摘要，不提供旧模型分析原文；当前消息始终优先。
- 当前轮情绪写入 usage 的 `emotion_before`；`emotion_after` 只能由下一次真实客户消息对应的 V3 决策回填。
- 开口、支付、排客、到店与完成使用送达后的时间窗口统计，不声明强因果；送达未知和平台订单查询失败必须单独统计，不能当作未回复或未成交。
- 平台订单归因只允许调用只读订单接口；失败保留既有事实并标记错误，不得覆盖为否。
- 送达回执未知时可以关联下一轮意图/情绪，但不得计算开口窗口或冻结订单窗口；收到真实 `delivered_at` 或平台接受时间后必须按新锚点重算。
- 平台订单查询按销售接触边界缓存原始订单，再按每个 usage event 的送达锚点和基线订单重新筛选；历史订单不能冒充本轮成交。
- 平台撤回、自动消息、去重/覆盖等协议事件可保留审计记录，但必须标记为非真实客户轮次，不得覆盖稳定策略状态、回填下一情绪或计入开口/订单归因。`test_isolated=true` 不写 usage，且其消息与 run 快照不得进入生产归因。
- usage 只保存策略 key、置信度、证据引用和纠正 reason code，不保存完整聊天、模型思维或原始模型输出。
- BI 中的逼单规则、策略和节点名称必须由本轮真实外部 ID 反查目录得到，模型自由文本不能作为业务名称。普通话术 `retrieval_match_scope` 区分 `checkpoint_type_tag_action|checkpoint_type_action|checkpoint_type_tag|checkpoint_type_semantic`；`retrieval_mode` 记录本轮最终候选使用的最宽范围。旧 `same_type_action_relaxed` 仅保留历史查询兼容，不再代表当前运行算法。

## 当前开关

- AI 销售策略通过 `AI_SALES_POLICY_ENABLED` 独立启用；逼单目录来源由 `AI_CLOSING_CATALOG_SOURCE` 选择，目录只提供候选，不替代当前 V3 回复。本地目录当前为 `provisional`，生产启用前仍需业务确认。
- 本地 `sales_strategy_catalog_v1` 保持退出 V3 Reply 运行链，仅允许离线评测或旧主动触达兼容使用。
- 延时逼单和四大区跟进维持 `shadow`：允许审计，不允许真实发送。
- 意向分只用于分析，不触发回复、逼单、开单或发卡。

## 交易与触达边界

- `closing_decision` 不授权开单、发卡或确认预约。
- 预约金卡要求同门店、同金额的真实有效未付订单。
- 人工接管、明确退订、已付、会话读取失败、客户已回复和重复发送阻止延时任务。
- 明确退订需写入同一销售接触边界的持久 stop-contact 事实；数据库短暂不可用时写本地安全日志，并在恢复后重放。所有主动触达发送前统一复核该事实。
- 延时任务按 `corp_id + wechat + external_userid` 隔离；平台客户 ID 仅用于平台接口，客户回复即取消旧节点并重新进入 V3。

## 启用前验证

先人工确认策略内容和素材事实；再由单独任务完成隔离模型验证、模拟生产生命周期和部署后验证。测试层级、结构化消息、持久化尾部及端到端性能必须遵循 [V3 Reply 质量与全链路评测规范](../standards/V3_REPLY_EVALUATION.md)。验证失败不得通过关闭事实过滤、订单校验、退订、人工接管、会话读取或 WeChat 隔离来绕过。

模型评测必须先完成全链运行阶段，再单独启动评审阶段；两阶段不得在同一 DeepSeek 配额窗口交错运行。报告分别统计策略结构覆盖率、检索召回率和“有候选且允许推进”的条件采用率，不得用全样本分母把未召回、明确退出或运行失败解释成模型拒绝采用。
