# AI 销售策略运行合同

- status: current
- owner: reply-runtime
- code_verified: 2026-09-10 Asia/Shanghai, `main@0e7f76e5`
- source_of_truth: `ai_paths/app/policies/ai_sales_policy_v2.json`、当前 V3 Reply/Router 代码、外部 Follow Knowledge 已发布目录及按配置启用的逼单目录

本文定义销售决策权、意图与情绪边界、跟进/逼单候选用法和客户可见动作约束。完整在线模型节点、Prompt 原文和动态上下文拼装见 [V3 大模型节点与提示词全景](../architecture/V3_MODEL_NODES_AND_PROMPTS.md)；代码和版本化配置始终是最终事实来源。

## 1. 唯一决策链

```text
客户当前消息、近聊和上一轮稳定摘要
→ 加载客户、订单、门店及已交付内容等权威事实
→ Semantic Router 规划事实工具和知识召回
→ 必要只读工具补齐事实
→ 跟进序列、卡点话术、逼单和素材候选
→ V3 Reply 同一次调用判断最终意图、情绪、销售状态、推进动作和回复
→ 代码校验事实、ID、权限、交易、安全与结构
→ 返回客户可见消息；异步补充策略观测和结果归因
```

- V3 Reply 是唯一销售语义决策点。不得再建立独立意图模型、情绪模型、序列选择模型或门店查询后的第二次销售判断。
- Semantic Router 只负责检索目标、卡点候选、事实工具和知识候选。其 `current_intent` 是检索摘要，不是最终销售意图。
- 代码负责权威事实、工具调用、稳定 ID、枚举、幂等、权限、发送结果和硬安全边界；不得用 Python 关键词分支代替正常销售判断。
- 跟进序列、话术、素材和逼单目录是参考证据，不是价格、门店、订单、预约、付款、效果承诺或实际送达的事实来源。

## 2. 统一决策输出

启用策略时，最终 Reply 在同一次模型调用中输出 `policy_decision`：

- `primary_task`：本轮唯一主任务。
- `secondary_tasks`：最多三个次要信号，不能独立触发客户动作。
- `realtime_intent`：最终主意图、最多三个次要意图、置信度和证据引用。
- `emotion_decision`：情绪、置信度、表达压力和流程动作。
- `cardpoint_decision`：当前卡点及 `none|active|repeated|resolved` 状态。
- `closing_decision`：`none|enter|advance|pause|fallback|complete`，以及真实规则、策略和节点引用。
- `customer_state`：销售是否继续、仅暂停本轮、硬停止或转为付款后服务。
- `next_sales_action`：本轮真正落实的唯一下一步。

主任务、主意图、客户状态、情绪流程动作和逼单动作属于运行字段；缺失或非法时最多使用一次已有修复机会。置信度、次要意图、说明和补充证据属于观测字段；缺失只记录 `decision_status=degraded`，不得导致 5xx 或额外模型调用。

已有完整 JSON 时，修复只允许纠正结构、真实 ID 和事实冲突，不得重新决定客户心理或销售策略；完全没有可解析结果时，唯一一次 full retry 才能重新执行原任务。Reply、full retry 和 targeted repair 使用同一 Reply 模型层，不静默切换供应商。

## 3. 最终意图目录

最终主意图只能来自以下七类：

| key | 含义 | 处理原则 |
| --- | --- | --- |
| `fact_inquiry` | 询问价格、效果、门店、时间、流程或规则 | 先直接回答；缺少权威事实时调用工具或说明暂缺 |
| `blocker_expression` | 价格、效果、信任、距离、时间、健康或决策成本构成阻力 | 先解卡，再判断是否恢复推进 |
| `transaction_progress` | 准备报名、预约、到店、付款或确认具体下一步 | 权威事实和交易条件齐全后执行一个合法动作 |
| `information_submission` | 回答上一轮问题，提交城市、门店、人数、联系方式或时间 | 承接已提交信息，不重复询问 |
| `defer` | 忙、改天、考虑或等待安排，但未拒绝后续联系 | 降压并交付一个低负担价值，不判流失 |
| `explicit_exit` | 明确要求不要再联系、不要再发或退出营销 | 立即停止商业营销并记录可审计事实 |
| `normal_exchange` | 确认、感谢、闲聊或表情，没有更具体任务 | 自然承接，不机械重开旧问题 |

- Reply 的 `policy_decision.realtime_intent.type` 是唯一最终意图；Router 的同名或类似字段只能用于检索。
- 同一句可保留次要意图，但一轮只能选择一个主任务和一个客户动作。
- 客户每次发新消息都要重新判断；上一轮意图和逼单节点只作稳定摘要，不得机械推进。
- 投诉、要求解释、找负责人或要求转人工本身不等于 `explicit_exit`。只有明确停止后续联系的原话才构成退订。

## 4. 情绪目录与边界

最终情绪只能来自以下八类：

| key | 最低证据 | 对回复的影响 |
| --- | --- | --- |
| `enthusiastic` | 明确认可、期待或主动行动 | 保持互动感，自然推进一个低摩擦下一步 |
| `curious` | 提出真实问题或请求进一步说明 | 先给结论，再补必要解释 |
| `neutral` | 没有足够证据归入更强情绪 | 正常、友好、简洁 |
| `hesitant` | 明确顾虑、比较、暂缓或难以决定 | 降压并处理权衡因素 |
| `cold` | 连续上下文中持续低参与、回避展开 | 缩短篇幅，只交付一个价值或问题 |
| `defensive` | 对我方真实性、效果、价格或证据明确质疑 | 用真实事实或案例回应，减少营销腔 |
| `impatient` | 明确嫌内容过多、催直接回答或反感重复 | 只答当前问题，暂停本轮追加销售 |
| `angry` | 强烈负面明确指向我方，且伴随投诉、威胁、转人工或要求停止当前销售 | 停止本轮销售，交由系统边界处理 |

- 单条短句、回复慢、标点、单个表情、单独粗口或口头禅都是弱信号，不能单独把客户判为冷淡、不耐烦或愤怒。
- 正向惊叹、抱怨自身/家人/第三方、普通讲价和一般质疑不是愤怒证据。
- `angry` 需要高置信度才停止本轮销售；低置信度只降压。它不自动构成永久退订。
- 情绪只能调整措辞、篇幅和销售压力，不能授权门店、价格、预约、付款、素材或效果承诺。
- BI 中的情绪变化仅表示两次真实客户消息分类发生变化，不得表述成某条回复直接改善或恶化客户情绪。
- 八类情绪为强制单标签；对“嗯、好、？”等信息不足输入必须同时展示低置信度，不能伪装成精确判断。是否增加 `uncertain` 只能基于业务金标混淆矩阵决定。

## 5. 客户状态和安全优先级

客户状态统一为：

| 状态 | 定义 |
| --- | --- |
| `continue_sales` | 正常沟通，以及讲价、考虑、没空、太远、普通质疑和单句粗口等软拒绝 |
| `pause_current_turn` | 客户正在开车、工作或明确要求本轮稍后再聊；只暂停当前轮，后续仍可合法唤醒 |
| `hard_stop_marketing` | 明确退订、人工接管、关系删除、医疗高风险或具体严重客诉/退款纠纷 |
| `post_payment_service` | 平台权威确认预约金已付，转入预约与到店服务 |

固定优先级是：健康/安全和具体严重客诉 → 人工接管 → 明确退订 → 权威交易终态 → 当前客户问题和销售动作。

- 明确退订、人工接管、关系删除不得被模型或业务配置覆盖。
- 医疗高风险和具体严重客诉应停止 AI 销售并转处理，但只有明确退订持久记录 stop-contact。
- “骗子吧、真的吗、太贵了、不用了”等单独出现仍属于可处理的质疑或软拒绝；只有具体描述我方服务损害、退款纠纷、骚扰或监管投诉才构成严重客诉。
- 已付不等于停止服务，而是禁止继续重复销售，转入预约、门店指引和履约承接。
- 首次输出中有客户证据且被代码核实的硬停止事实构成修复下限，修复不得改成继续推进。

## 6. 主线和真人表达

销售主线按真实已交付事实判断：

```text
需求 → 效果/项目 → 活动价值与价格 → 门店 → 预约意愿 → 预约金 → 付款后服务
```

- 当前问题和明确请求永远优先。客户可以跳问，事实与权限齐全时应当轮回答或交付；`next_missing_stage` 只表示相邻销售机会和不可越过的上限，不是每轮必须执行的流程任务。
- 每个正常轮次仍必须记录一个非空 `next_sales_action`，且客户可见文字或结构消息要与已落实动作一致。关系承接、短回应、临时不可交流、重复暂缓和只纠正表达时，`keep_open` 是完整且合法的动作。
- 一轮只有一个主目标，不同时堆门店、时间、名额和预约金。客户当前问题处理后，只有仍适合交流且衔接自然时，才推进一个相邻方向；直接发送案例、门店卡或合法付款卡也是有效动作。
- 临时不可交流与软拒绝必须分开：开车、工作、休息或明确稍后聊时，只短承接，不补销售价值、不追问时间；首次无原因软拒绝且历史未问过时低压澄清真实顾虑；原因明确时处理对应顾虑；已经问过仍重复暂缓时只短接并 `keep_open`，不重复盘问或塞同一价值。
- 不设默认消息数、单条最低字数或固定“承接＋解释＋价值＋CTA”骨架。短回应可以只有几个字；答题和事实交付按需要展开。每轮最多 8 条客户可见消息、文字合计最多 300 字只是异常保护，不是创作目标。
- 禁止同义重复、客服菜单、Router/培训稿/内部审计措辞和机械截句。客户只要求“说人话/别总结”且没有业务请求时，只做自然短承接，不恢复价格、效果、门店或预约话题。普通销售轮最多使用一个自然轻表情；投诉、退款、医疗风险和付款核验不使用表情。
- 已具备且允许直接交付的价值不得再问“要不要看/要不要发”。

## 7. 跟进、卡点与逼单候选

### 普通跟进

- 外部 Follow Knowledge 是普通跟进序列、卡点 taxonomy 和卡点话术的在线权威目录；本地同步数据只用于离线评测和取证，不参与线上隐式降级。
- 卡点类型是普通话术的硬边界；动作、标签、Router 焦点和序列节点只参与排序，不得因为动作或标签不完全一致把同类型候选过滤为零。
- 向 Reply 提供受字符预算约束的少量多样候选，不跨卡点类型填数；卡点目录为空或接口不可用时必须如实记录，不能伪造知识。
- 跟进序列描述节奏，卡点话术解决当前顾虑，两者可以独立采用。活跃或重复卡点已有直接相关、无事实冲突且压力合适的话术时，Reply 应采用一个并记录真实 `script_id`；全部不安全或不相关时可以不采用，但必须记录原因。
- `cardpoint_decision.state=active|repeated` 时先解卡并暂停逼单；只有模型明确判为 `resolved`，代码核对证据后才允许重新进入或推进逼单。

### 逼单

- 逼单规则回答“当前场景是否具备资格”，策略回答“采用哪套节奏”，节点话术类型回答“从哪类表达取材”。三者只是候选，不直接授权客户动作。
- `enter|advance` 必须引用本轮同一逼单目录中的真实 rule、sequence、node ID，并通过前置项、禁忌、频控、时机和话术类型校验。
- 逼单节点的 `followCheckpointTypeId` 是同一目录内话术类型外键，必须严格匹配；不得跨类型补逼单话术。
- 逼单目录来源由显式配置选择：`external`、`local` 或 `external_then_local`。同一轮不得混用来源，必须保存来源和 checksum；本地目录不得伪装成平台数字 ID。
- 外部规则和策略正常且非空时，`external_then_local` 优先外部；本地目录只是在业务接口未就绪时的版本化替代，不证明任何动态业务事实。
- `combined` 规则在上游没有明确组合分组及 AND/OR 关系时只记录、不可执行。
- `delay>0` 的节点只能作为 Shadow；即时回复不得自动发送延时节点。Shadow 也不能绕过新客户消息、退订、人工接管和交易终态。
- `closing_decision.action=none|pause` 不表示销售主线停止。无可执行逼单序列时，仍可正常回答、解卡或推进相邻主线。

## 8. 素材、价格、门店和交易事实

- 效果、信任或使用效果证据解卡时，只要有相关、未发送且无冲突的真实素材，应同轮按“短文字 → 图片/视频”交付一个最相关素材组，不再询问是否需要。素材必须来自本轮候选，且按稳定 ID、文件哈希或感知指纹避免重复。
- `knowledge_use.script_id` 表示采用的文字依据，`selected_content_ids` 表示实际结构媒体；二者不能互相冒充。没有真实媒体候选时只能文字回答。
- 公开门店地址可以在付款前发送。门店工具得到唯一真实 `delivery_store_id` 时，同轮必须交付自然说明和对应 `store_address` 卡；无工具事实不得猜地址。
- 楼层、房间、门面号、接待方式和详细导航属于到店指引，只有权威已付且门店确定后才可交付。客户口头声称已付必须先核验。
- 门店没有权威营业时间时不得输出具体时段；应说明尚未同步，并记录内部事实待办。事实待办不是外部工单，也不承诺处理时效。
- 价格、活动、预约金、退款/抵扣和付款入口必须来自本轮权威事实。目录只证明推荐表达，不证明动态事实成立。
- 首次只问价格时可以解释权威活动价、包含价值和已有事实支持的预约金机制，但不得直接发送付款卡；客户明确报名、预约、怎么付或索要入口，且订单、金额和付款结构齐全后，才可同轮发真实付款卡。
- 交易动作只能由 V3 Reply 明确选择，并通过现有工具 schema、金额、门店、订单、幂等和提交结果校验。逼单决策本身不能授权建单、预约或付款。

## 9. 跨轮状态和 BI

- 上一轮状态只读取同一 `corp_id + wechat + external_userid` 销售接触边界内最近一条稳定事件；`platform_customer_id` 只作独立平台记录 ID，不能替代外部联系人 ID。不同企微不得共享客户状态、发送次数、订单或策略进度。
- 当前 Reply 只接收上一意图、情绪、活动卡点、逼单节点、是否已发送、客户是否已回复和订单是否变化等稳定摘要，不接收完整旧模型分析。
- 下一次真实客户回复可回填上一事件的下一意图、下一情绪及变化；平台协议消息、撤回、去重覆盖和隔离评测不算真实下一轮。
- BI 可记录意图、情绪、卡点、规则、序列、节点、话术、候选/采用/送达、客户开口和订单时间窗口。完整聊天原文和模型思维不得进入策略事实表。
- 送达未知不进入送达转化分母；订单未知或查询失败不得写成未成交。所有结果只是时间窗口相关性，不宣称策略直接导致成交。
- 策略观测写入失败不得影响客户回复。历史没有保存采用详情时显示“未记录”，不得用当前目录或 Router 候选反推当时采用。

## 10. 验收和演进

- Prompt、候选排序、情绪或销售节奏改动属于回复质量改动，必须先通过确定性边界测试，再用相同 DeepSeek 配置和同批匿名样本对照。
- 必测边界包括：当前问题优先、软拒绝继续价值交付、粗口不误判愤怒、明确退订零误推进、医疗和严重客诉、素材/门店结构交付、付款事实、跨企微隔离和 Shadow 零发送。
- 模型初评只能用于发现问题；主意图、情绪、真人表达和逼单适当率必须由业务确认样本形成金标后才能宣称准确率。
- 若简化 Prompt 或检索链造成回复、安全、候选条件采用或延迟明显退化，应回退该改动，而不是继续追加相互冲突的例外。
- 动态目录版本、条数、生产模型、开关和线上指标写入 `docs/current/` 或 ignored `artifacts/`，不得固化在本合同。
