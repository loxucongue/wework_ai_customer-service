# 母窗口与子窗口协作规范

- status: active-workflow
- owner: project mother window / integration owner
- source_of_truth: 项目宪法、任务索引和当前 main

## 1. 角色划分

| 角色 | 负责 | 不负责 |
| --- | --- | --- |
| 母窗口 | 产品讨论、需求澄清、优先级、方案审核、子任务拆分、冲突协调、结果验收 | 长日志诊断、批量测试流水、同时修改多个模块、从旧工作区直接部署 |
| 执行子窗口 | 单一明确任务的取证、设计、实现、测试和任务内文档 | 扩大产品范围、修改其他任务文件、未经授权上线、替母窗口决定重大业务取舍 |
| 集成窗口 | 审查提交、解决冲突、合入 main、发布前检查和部署 | 使用整分支覆盖、跳过验证、修改不在任务合同内的业务规则 |
| 评测子窗口 | 按冻结样本和口径执行 L1–L4 测试、输出脱敏报告 | 把 AI 初评冒充业务金标、发送客户消息或生产写入 |

母窗口可以指定自己或某个执行窗口兼任集成窗口，但同一批合并只能有一个明确集成人。

## 2. 什么留在母窗口

母窗口只保留能影响产品决策的短信息：

- 当前目标和为什么做。
- 已确认业务规则及其变更。
- 活跃子任务、负责人、状态和文件边界。
- 需要产品选择的冲突或风险。
- 测试结论、上线结论和未达到项。

以下内容不贴入母窗口，放在任务文件或 ignored `artifacts/`：

- 完整客户聊天、真实身份和原始线上日志。
- 大段 JSON、Prompt 展开、模型原始输入输出。
- 完整测试控制台输出、CSV、截图和浏览器产物。
- 逐文件修改过程、临时代码和失败重试流水。

子窗口回报母窗口时使用五项摘要：`结论 / 改动 / 证据 / 风险 / 下一步`。

## 3. 从讨论到执行

```text
母窗口收到需求
  → 对照 MASTER_CONTEXT 判断是否重复、冲突或依赖外部数据
  → 明确产品目标、非目标、验收与权限
  → 拆成互不重叠的子任务
  → 在 active/INDEX 登记 task、branch、base、worktree 和文件范围
  → 创建独立子窗口
  → 子窗口实现并提交
  → 集成窗口 review、测试、合入 main
  → 经明确授权后发布
  → 更新合同/current/history，关闭 task 和 worktree
```

讨论阶段可以并行安排只读取证，但未确定产品边界前不得让多个子窗口同时修改同一模块。

## 4. 子任务包的必填内容

母窗口派发前必须给子窗口一份足够独立执行的任务包：

1. `task_id`：稳定、简短、可作为 `codex/<task-id>` 分支名。
2. 背景和目标：用户看到的问题、期望业务结果。
3. 非目标：本轮明确不处理什么。
4. base：执行时最新 `origin/main` 完整 SHA。
5. 独占范围：允许修改的文件或目录，和不得触碰的活跃任务范围。
6. 权威文档：必须读取的架构、合同、接口和当前状态。
7. 数据/模型/发送权限：默认本地、假模型、零生产写、零客户发送；例外必须明确批准。
8. 验收标准：确定性测试、模型评测、性能、业务人工复核和发布检查分别要求什么。
9. 发布范围：只提交、合入 main、部署后端、部署前端或只读核验。
10. 回滚条件：什么失败必须停止或恢复上一 release。

缺少会改变实现方向的产品选择时，子窗口应回母窗口审核，不能自行扩大范围。

## 5. 子窗口启动模板

```text
读取 AGENTS.md、docs/INDEX.md、docs/current/MASTER_CONTEXT.md、docs/tasks/active/INDEX.md 和 docs/tasks/active/<task-id>.md；再读取任务列出的相关架构、合同和接口文档。

先核验当前 branch、HEAD、dirty 状态、最新 origin/main 和其他活跃任务文件范围。只能在登记的独立 codex/<task-id> 分支和 worktree 内工作，不修改其他任务占用文件，不清理用户未提交内容。

严格按任务文档的目标、权限、验收和发布范围执行。重要证据写入任务文档；客户原文、原始日志、模型输出和测试报告只写 ignored artifacts。完成后提交任务分支并按“结论、改动、证据、风险、下一步”向母窗口汇报；除非任务明确授权，不自行合并 main 或部署。
```

## 6. 并行与文件所有权

- 并行的前提是子任务可以独立推进且文件范围互斥；只是为了显得快而拆分会增加冲突，不应并行。
- `docs/tasks/active/INDEX.md` 是所有窗口的所有权登记表。两个任务不能同时声明同一核心文件。
- 同一文件内的小映射、Prompt 和校验改动优先由一个子任务完成，不拆成多个窗口互相覆盖。
- 共享 schema 或接口必须先由一个任务锁定合同，再允许其他任务基于该合同并行。
- 子窗口发现必须修改别人占用的文件时立即停止该文件修改，向母窗口报告；不得先改后通知。
- 只读日志分析可以并行，但原始日志不写入 Git，也不把客户身份贴回母窗口。

## 7. 分支、提交和集成

- 新执行任务从当时最新 `origin/main` 建立干净 `codex/<task-id>` 和独立 worktree。
- 旧分支只能取证；不能整分支合并、全局选择 ours/theirs 或覆盖 main。
- 子窗口按功能边界提交，提交信息说明模块和效果；无关修改不夹带。
- 集成窗口先检查其他 worktree 的已提交/未提交状态，但不得擅自提交、删除或清理不属于本任务的内容。
- 发生冲突时逐文件比较“最新版合同、当前 main、两个任务的具体行为”，需要产品取舍的冲突回母窗口审核。
- 合入前重新同步 origin/main；验证通过后优先 fast-forward 或显式小范围合并。
- main 是唯一长期分支。临时分支合并后删除，worktree 移除；用户 dirty 工作区保持原样。

## 8. 测试和发布权限

- 默认子任务无权调用真实模型、读取真实客户原文、发送消息、生产写入或部署。
- 真实身份测试必须经母窗口明确批准，并采用只读事实、阻断所有发送/写入、脱敏输出和生产反查零记录。
- “测试通过”必须写清 L1、L2、L3 或 L4；不允许把模型图通过写成生产全链通过。
- “合入 main”不等于“已上线”。部署任务必须另有发布、迁移、回滚和现场核验权限。
- 三个后端角色从同一 clean main SHA 发布；耦合前端同批；任何角色 dirty、SHA 不一致或迁移失败都停止发布。
- 线上异常先保护客户请求和现有数据，再诊断；不得用未经测试的全局开关或数据库破坏性操作抢修。

## 9. 子窗口完成回报模板

```text
结论：完成 / 未完成 / 被阻塞，以及用户可见结果。

改动：按产品板块列出实际改变，不贴大段 diff。

证据：提交 SHA、测试层级与数量、性能数据、隔离审计、是否部署及生产 SHA。

风险：仍未验证、依赖业务/第三方、可能与其他模块交互的部分。

下一步：母窗口需要审核的选择，或可以直接关闭任务的依据。
```

母窗口不得只看到“测试都通过”就批准上线；必须核对测试是否覆盖当前业务状态、结构消息、数据库尾部和真实发布拓扑。

## 10. 母窗口验收清单

- 需求是否真的解决，而不是只改了日志或 Prompt 表面。
- 当前问题、目标用户和业务状态组合是否进入测试。
- 是否误改 V3 唯一决策权、客户身份边界、明确退订或交易事实边界。
- 是否引入额外模型节点、重复数据库链路、隐式 fallback 或第二套规则。
- 代码、迁移、前端、接口和文档是否来自相同合同版本。
- 测试结论有没有把 AI 初评、平台受理、发送和送达混为一谈。
- 是否保留用户已有 dirty 工作区和其他任务的文件。
- main 是否干净、提交是否完整、发布角色和回滚点是否明确。

## 11. 文档更新责任

- 产品规则改变：执行任务更新对应 `contracts/`，母窗口同步 `MASTER_CONTEXT.md` 摘要。
- 组件或数据流改变：更新 `architecture/`。
- 外部或公共接口改变：更新 `interfaces/` 和专项合同。
- 动态生产事实改变：更新 `current/PRODUCTION_STATE.md`，不得写进稳定合同。
- 新风险或关闭风险：更新 `current/KNOWN_ISSUES.md`。
- 单次任务过程：只写对应 active task；完成后历史索引一行，详细内容回查 Git。
