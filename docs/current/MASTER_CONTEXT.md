## 1. 这份文档解决什么问题

本页把长期讨论中已经确认的产品方向、工程边界、当前完成度和待决事项收敛成一个母窗口入口。母窗口用它与产品负责人讨论、拆任务、审核方案和验收结果；实现细节交给独立子窗口，不再把所有开发、日志诊断、测试和发布堆在同一个聊天中。

本页不保存聊天逐字稿、真实客户日志、截图、模型原始输出、Token、密钥或一次性测试报告。需要追溯某次实现时查 [任务历史](../tasks/history/INDEX.md) 和 Git；需要看当下线上状态时重新核验 [生产状态](PRODUCTION_STATE.md)。

事实优先级固定为：

```text
当前 main 代码与版本化配置
  > 专项合同 / ADR
  > 带核验时间的 docs/current 快照
  > 本母窗口摘要
  > 历史任务摘要和旧聊天
```

## 2. 产品北极星

AI Paths 不是被动问答机器人，而是企业微信淡斑活动的销售接待系统。目标是在不编造价格、效果、门店、订单、预约和支付事实的前提下：

1. 先准确回答客户当前问题。
2. 给客户一个有用、真实、低摩擦的价值或下一步。
3. 正常介绍需求、效果、活动、门店、预约意愿和预约金主线。
4. 出现卡点时用跟进序列、卡点话术和真实素材解卡，再继续主线。
5. 达到业务 B 单条件时选择合适策略推进；不满足时不机械逼单。
6. 客户沉默后，在 AI 托管、安全门禁和真实跟进节奏下主动唤醒。
7. 用日志和 BI 看清“识别了什么、用了什么、是否发送、客户是否开口、订单是否变化”。

## 4. 已确认的产品决策

以下是已经反复确认、后续任务不应重新从零争论的默认决策。若产品负责人明确改变，应先更新对应合同，再实施代码。

### 4.1 决策权和模型链

- 只保留产品 V3 Reply；不得恢复 V1/V2 产品回复路由。
- 所有 `slXXXX` 当前都是同一业务知识租户下的不同接待企微号，可以共享租户级 Follow Knowledge 凭证、知识目录和只含业务知识的缓存；客户聊天、订单、画像、发送次数、SOP 和主动唤醒状态仍严格按企微隔离。
- V3 Reply 是唯一销售语义决策者。Semantic Router、意图/卡点证据、序列、话术、B 单目录和门店工具都只能提供事实或候选。
- 正常链目标是一次 Router、必要事实工具、一次最终 Reply；post-store 不再做第二次销售语义判断。
- 模型负责客户语义、心理、节奏和自然表达；代码负责事实、工具、合法 ID、schema、幂等、权限、发送和硬安全边界。
- 当前文本 Router 和 Reply 使用 DeepSeek；最终 Reply、完整重试和定向修复不得回退 GPT。图片理解和门店目的地解析的实际模型边界以生产状态和 run trace 为准。
- 一轮应用层最多一次完整重试或定向修复；BI 字段缺失不能触发第二次业务判断或让客户请求失败。

### 4.2 真人销售表达与主线

- 当前问题必须先答，回答后只推进一个相邻方向；不能同时堆效果、价格、门店、时间、名额和预约金。
- 客户可以跳着问，不机械念固定流程；答完后回到最早尚未真实交付的主线：`需求 → 效果/项目 → 活动/价格 → 门店 → 预约意愿 → 预约金 → 付款后服务`。
- 不再限制默认只能一条消息。答题、证明、推进可以拆成多条短微信；8 条/300 字只是异常上限，单条以短、口语、易读为目标。
- 普通销售轮可以使用一个自然轻表情，不能每句堆表情；投诉、退款、医疗风险和付款核验不用表情。
- 禁止客服菜单、内部审计腔、同义重复和“要不要我发活动价/效果图”这类无效往返。可以直接提供的真实价值应直接交付。
- 每个正常销售轮都要在客户可见文字或结构消息里落实一个 `next_sales_action`，不能只在日志字段里写计划。

### 4.3 意图、情绪和营销停止边界

- 最终意图使用 7 类，最终情绪使用 8 类；Router 的检索意图不是最终标签。
- 单句粗口、讲价、质疑、催回复、短句或标点不能单独判为高置信愤怒，也不能永久停止营销。
- “没空、考虑一下、晚点、太远、贵、不用了”等普通拒绝属于可处理的软拒绝；应降压、换价值角度继续，不得直接放走客户。
- 客户正在开车/工作并明确要求稍后，只暂停当前轮，后续仍可合法唤醒。
- 明确退订、人工接管、关系删除、医疗高风险或具体严重客诉/退款纠纷才进入硬停止边界；其中只有明确退订形成持久 stop-contact。
- 平台权威确认预约金已付后转入预约和到店服务，不再重复营销或催预约金。

### 4.4 卡点、跟进序列和话术匹配

- 有卡点时应尽量同时得到可用跟进序列和卡点话术，但不能为了 100% 采用率强用错误内容。
- 普通卡点类型是话术召回硬边界；动作和标签只是排序证据。平台标签不完善时，不得因“动作/tag 不完全一致”把同类型话术过滤为零。
- 每轮只向 Reply 提供受预算约束的少量、多样候选；不能把整个话术库塞进上下文。
- 跟进序列提供节奏，卡点话术提供当前表达，两者允许独立采用。存在直接相关、压力合适且无事实冲突的话术时应采用一个并保存真实 ID；全部不安全时必须说明未采用原因。
- 卡点未解决时 B 单暂停；模型明确判定卡点已解决并有证据后，才允许进入或继续逼单。
- 业务期待的安全候选采用率是约 80%–90% 以上，不追求错误的机械 100%。

### 4.5 B 单规则、策略和话术

- B 单规则回答“什么时候可以开始”，来自业务销冠总结的场景；规则命中仍需 AI 结合完整上下文确认。
- B 单策略回答“当前适合用哪套节奏”；节点的 `followCheckpointTypeId` 指向对应 B 单话术类型。
- `enter/advance` 必须引用同一真实目录中的规则、策略和节点 ID，并满足前置、禁忌、频控和当前事实。
- 外部业务平台最终是正式在线权威；业务接口未就绪期间允许使用版本化本地 provisional JSON，但必须标明来源和 checksum，不能伪装平台数据或同轮混用。
- 即时 B 单可以影响当前回复；延时 B 单和四大区节点保持 Shadow，不自动发送。
- B 单决策不能授权付款、预约成功、门店、名额或效果承诺。

### 4.6 效果素材

- 客户询问效果、表达信任顾虑，或 Reply 决定用案例解卡时，只要存在相关、未发送且安全的真实素材，应同轮“短文字 → 图片/视频”直接交付。
- 不再问“要不要我给您发效果图”；也不能只承诺“我发您”却没有结构消息。
- 优先一个最相关案例组；客户明确要求多看时可以给 2–3 个不同案例组。
- 素材按稳定 ID、文件哈希和感知指纹去重，换 URL 的同一图片也不应重复发。
- 内容属于错误项目、过期或业务不适用时由业务目录治理；代码保证来源、去重和事实边界，不能替业务判断素材内容是否正确。

### 4.7 门店工作流

- 客户提出门店场景时必须经过门店工作流取得权威结果；没有工具事实不能猜地址、距离、停车、营业时间或楼层。
- 唯一门店结果同轮直接发送自然说明和真实门店卡，不再问“要不要发地址”。
- 最近实际发送的门店卡与最近区域推荐依据是两份不同事实：前者防重复，后者决定是否值得重查。
- 当前城市范围已经完成推荐后，客户说“太远”时不再追问地铁站、路口、楼栋等无效细地址；先用距离卡点话术转向技术、效果和案例。只有客户提供新的城市，才重新匹配。
- 没有真实距离数据时不能客观断言某店近或远，只能承接客户主观感受。
- 停车、已发布营业时间属于公开门店详情；楼层、房间、门面号、接待方式和详细到店指引只在权威已付且唯一门店确定后交付。
- 门店没有权威营业时间时不得编造具体时段；记录内部事实待补，但不能承诺处理时效。
- 已发门店卡后问停车、营业时间等详情不重复发卡；客户明确再次索要地址或导航时允许重发。

### 4.8 价格、预约和付款

- 当前活动 268 的业务边界是面部斑点改善部位；两侧脸颊按实际斑点位置处理，不拆成两个价格，也不表述为无差别“全脸操作”。
- 面部和手部是两个部位，不能合计只报一个 268；二次或后续价格不能自动沿用 268，应以届时活动和门店权威确认为准。
- 首次只问价格时直接回答权威活动价、包含价值和允许说明的预约金机制，但不自动发送付款卡。
- 客户明确报名、预约、怎么付或索要入口，且订单、人数、金额和付款结构齐全后，同轮可以直接发送真实预约金卡。
- 客户文字声称已付只作声明；支付截图成功、平台支付事件或权威订单状态才证明已付。
- 发门店地址不等于已预约；询问到店时间也必须有明确预约目的，不能虚构已经登记、保留档期或可以直接到店。

### 4.9 沉默唤醒

- 当前沉默唤醒覆盖全部企微号，只处理平台明确为 AI 接待的客户；人工状态不处理。
- 候选沉默阈值为 1 分钟，不限制加微时间。1 分钟只是进入候选资格，不是第 60 秒准时发送 SLA。
- 客户必须真实开过口；同一沉默周期只能有一个有效计划，客户重新开口后才形成新周期。
- 有卡点时按真实跟进来源续接尚未发送的不同节点；当前计划会控制重复价值，并在解卡后只承接一个成交动作。历史 `first_day_*` 只是兼容名称，不代表首日限制。
- 不使用“每天最多 2 个计划/4 个任务”的旧限制；普通非沉默 Outreach 的独立限制不应混入沉默唤醒。
- 普通夜间计划顺延；客户夜间仍活跃时，完整计划可压缩在最后消息后的 40 分钟内，但不能丢失逐次发送安全检查。
- 制定计划前和每个发送节点前都检查 AI/人工、客户新消息、退订、关系删除和订单终态；订单查询失败或状态未知时保守不发。
- 主动唤醒使用真实发送接口；B 单延时 Shadow 不是主动唤醒，不得混为同一发送链。

### 4.10 失败恢复、幂等和性能

- 正常业务请求不得以空回复伪装成功。空结果只允许被更新消息取代、协议过滤或明确人工接管等可审计终态。
- 同步最终失败的唯一中性文本是“您稍等一下”；不再要求客户重新发送问题。
- 客户可见自动失败补答能力当前保持关闭，只有完成真实发送、回调、取消和幂等专项验收后才能单独启用。
- 身份和 `msgid` 完整时，同一平台消息只生成一个 run 和一组稳定 `response_id/client_message_id`；聚合平台仍需按该 ID 做下游发送幂等。
- 实时正常 V3 回复通过 HTTP 返回给聚合平台；AI Paths 不在同一请求里再调用主动发送接口。
- 性能必须区分入口、Router、知识/工具、Reply、核心持久化、HTTP 总耗时和异步收尾。只测模型图不能称为接口端到端速度。
- 非关键轨迹、画像、BI、Shadow 和 outbox 使用持久、幂等的收尾 Worker；不能用进程退出会丢失的临时后台任务换速度。

### 4.11 BI、日志和数据口径

- AI 回复日志需要能一眼看到客户原话、最终回复、最终意图、情绪、卡点、B 单动作、候选序列/话术、最终采用、结构素材、节点状态和完整耗时；原始 JSON/Prompt 按需下钻。
- Router 判断与 Reply 最终判断必须分开；候选、采用、实际发送和最终送达必须分开。
- 历史字段没有保存时显示“未记录”，不能显示虚假 0，也不能用当前目录反推当时结果。
- 主动唤醒看板按客户展示企业、企微、外部联系人、平台客户、加微关系、会话、计划、任务和平台消息 ID。
- 平台发送接受状态只是“有发送证据”，不等于客户已送达；订单状态变化阻断也不能直接命名为预约或支付转化。
- 结果只做 1h/6h/24h/72h 开口和订单时间窗口相关性，不宣称某条策略直接导致成交。
- BI 表不保存完整客户聊天原文和模型思维过程。

### 4.12 测试、提交和上线

- 用户说“全场景”时，必须按完整状态组合测试，不只是按价格、门店、卡点等消息类别抽样。评审必须读取文字和结构消息。
- L2 模型图评测不能证明真实结构消息去重、数据库尾部或 HTTP 总耗时；完整结论必须按 L1–L4 分层。
- AI 评审只算初评；正式意图、情绪、真人感和 B 单准确率需要业务确认金标。
- 默认测试不调用真实模型、发送或生产写接口。经明确批准的真实身份测试必须只读、零发送、零生产写并反查隔离结果。
- 质量测试使用 DeepSeek 时，报告必须区分 DeepSeek 候选效果与实际生产模型配置；不能偷换分母或供应商。
- 新功能从最新干净 `origin/main` 创建独立任务、分支和 worktree，先登记文件所有权；主 Agent 审核后合入 main。
- 三个后端角色必须使用同一个 clean main SHA；耦合的前端改动同批发布。不得从 dirty、detached 或旧分支直接部署。
- 没有现场迁移、回滚点、服务角色、健康和接口验证证据时，不得把“代码完成”写成“已上线”。

## 5. 当前未闭环优先级

母窗口每次讨论新需求前，先判断它是否属于以下已知工作，不要重复创建同义任务。精确关闭条件以 [已知问题](KNOWN_ISSUES.md) 为准。

### P1：优先安排

1. 建立 400 条业务人工金标，并让销售主管复核真人感、表情和推进强度。
2. 将临时 B 单 JSON 切换为业务平台正式规则、策略、节点和话术目录。
3. 审计策略 outbox 历史 pending/dead 后再决定是否恢复外发。
4. 独立治理 RDS 公网链路长尾，验证同 VPC 内网连接和回滚。
5. 将前端改为站外构建或降低服务器构建峰值，关闭 OOM 风险。
6. 完成客户可见失败补答的真实发送安全验收，再决定是否启用。
7. 与聚合平台共同验证稳定消息 ID 是否真正阻止客户侧重复发送。

### P2：持续完善

1. 业务持续治理素材和话术目录版本、过期内容及错误项目内容。
2. 第三方补齐门店营业时间和付款后到店指引。
3. 建立稀有生命周期状态矩阵，尤其是结构卡已发、阶段状态和当前异议的组合。
4. 定义沉默唤醒从资格到计划、发送的产品 SLA，并在看板显示真实时间点。
5. 优化 30/90 天主动唤醒审计查询，不放宽客户身份边界。
6. 分批治理历史客户身份混用，只接受平台验证映射。
7. 对超大核心模块做独立、无行为变化的职责拆分；不能边改销售语义边重构。

### 已明确暂缓

- 第三方 `global-setting`、`intent-judgment`、`decision-routing` 三个“AI 大脑配置查询”接口暂不接入当前 V3。它们只提供配置，不执行客户判断；未来若恢复，必须先审核与现有 Reply Prompt、7 类意图、策略 BI 和流程安全门的重叠，分页拉全并校验各页 `version`，且不能因此增加第二个销售决策者或拉长正常回复链。

## 6. 需要产品或外部系统配合的事项

| 事项 | 需要谁提供 | 系统在缺失期间的行为 |
| --- | --- | --- |
| 正式 B 单目录 | 业务将规则、策略、节点话术导入第三方平台 | 使用显式 provisional 本地目录并标明来源，不伪装正式数据 |
| 素材/话术业务质量 | 业务提供过滤后的目录版本或 checksum | 只保证来源、去重和事实边界，不能宣称内容已业务验收 |
| 门店营业时间/到店指引 | 第三方平台补权威字段 | 不编造具体时段、楼层或接待方式 |
| 正式回复金标 | 销售主管逐条确认或修正样本 | AI 指标仅标记初评，不作为正式准确率 |
| 聚合平台发送去重 | 聚合平台按 `client_message_id` 幂等并提供发送/回调日志 | AI 侧只保证稳定生成与消息 ID，不能单方证明客户侧不重复 |
| RDS 内网链路 | 运维提供同 VPC 地址、窗口和回滚方案 | 继续观测公网长尾，不把代码优化冒充网络问题已解决 |

## 7. 母窗口如何工作

母窗口只做以下工作：

1. 与产品负责人讨论需求、纠正假设、确定产品取舍和验收标准。
2. 判断需求是已实现、配置/数据问题、代码缺陷、新功能还是外部依赖。
3. 把批准的工作拆成一个或多个互不冲突的子任务，并指定目标、非目标、文件范围、验证、是否允许模型/数据/发送和是否上线。
4. 创建或要求创建独立子窗口；母窗口不在自己的聊天里展开长日志、完整测试输出或大段实现过程。
5. 接收子窗口的短汇报，只审核结论、证据、冲突、风险、提交和发布状态。
6. 产品决策改变时更新本页和权威合同；实现细节只进入专项合同、任务历史和 Git。

完整流程见 [母窗口与子窗口协作规范](../tasks/PARENT_CHILD_WORKFLOW.md)。

```text
收到需求后先判断：是否已经实现、属于代码/配置/业务数据/第三方接口/运维哪一类、是否与现有任务冲突、需要哪些验收证据。方案经我确认后，再为执行工作创建独立子窗口和 task 文档；每个子窗口独占分支、worktree 和文件范围。母窗口只保留产品决策、任务状态、风险与结论，不接收客户原文、完整日志、模型原始输出或大段测试流水。
```

## 9. 维护规则

- 新的长期产品决策：先更新专项合同，再同步本页的摘要或优先级。
- 新的动态线上事实：只更新 `docs/current/PRODUCTION_STATE.md`，本页只链接，不复制易过期数值。
- 新任务：登记 `docs/tasks/active/INDEX.md` 和独立任务文件，不把待办直接追加成无限清单。
- 任务完成：长期结论进入合同/ADR，历史索引留一行，删除活跃任务文件。
- 旧讨论被推翻：直接修改当前合同和本页，不保留两套并列“现行方案”；历史由 Git 追溯。
- 本页每次大版本治理后重新核对链接、敏感信息和与代码/合同的冲突。
