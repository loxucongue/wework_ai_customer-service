## 同步 V3 模型链

当前正常链只有四类在线模型用途：条件图片理解、必经 Semantic Router、条件门店目的地解析、
必经最终 Reply。Reply 无 JSON 时可完整重试一次；已有 JSON 但校验失败时只做一次定向修复。
序列/话术筛选、post-store 补召回、事实校验和素材拼接均为确定性代码，不是额外销售模型。
详见 [V3 大模型节点与 Prompt 全景](../architecture/V3_MODEL_NODES_AND_PROMPTS.md)。

## 最近稳定验证

- 当前生产后端发布前通过 853 项仓库回归和第三方 SOP 专项回归；这是代码合同证据，不是业务金标准确率。
- 素材恢复工具通过全仓 1010 项、隔离 MySQL 8 专项 42 项、生产规模 1000 条合成目录性能和虚构身份零发送 L2/L3；生产以 5 条单批完成 47 个身份批次和 5 个历史占用批次，重入复验无新增写入。生产自然流量观察期没有新增 V3 run，因此这里只证明候选资格恢复，不证明第三方实际发送或送达。
- 已有 DeepSeek L2/L3 隔离样本证明结构、事实、安全和部分真人表达可运行，但历史聚合百分比不能代表完整生产状态组合或正式业务验收。
- 生产日志已能区分完整 HTTP、Router、工具、Reply、核心持久化和异步收尾耗时；单个样本或模型图耗时不能替代 P50/P95/P99。

## 尚未闭环

1. 400 条业务人工金标仍未完成；真人感、表情自然度和销售推进需销售主管复核至少 50 条自然请求。
2. 临时本地 B 单目录仍是外部接口不可用时的 provisional 兜底，待业务把正式目录导入第三方平台后验收切换。
3. 错误、过期或超过 6 MiB 的素材只能由业务目录治理解决；代码只保证来源、相关候选、去重和事实边界。历史 2,216 条无法与当前目录精确匹配，其中 4 条还缺完整 contact 边界，不能猜测补占用。
4. 门店营业时间和付款后到店指引字段仍不完整；系统当前只能不编造并记录待补事实。
5. RDS 公网链路和生产构建内存峰值仍可能制造长尾或 OOM；属于独立运维治理。
6. 自动失败补答保持关闭，需完成真实发送、回调、恢复后素材/门店记忆收尾的专项验收后再启用。
7. 聚合平台是否按稳定消息 ID 去重需要双方日志验证，AI 内部幂等不能替代下游发送幂等。
