# V2 与主动 SOP 销冠节奏优化发布审查

## 结论

- 目标链路保持模型主导：Gate 提名内容资产，Tool Planner 查询只读事实，Reply 负责客户语义、销售节奏和最终回复；代码只校验事实、引用、结构、支付安全、频率和发送边界。
- 未新增销售状态机、客户意向打分、Python 关键词业务分流或“客户说 X 就执行 Y”的微场景分支。
- V2 实时回复已经具备“回答当前问题后直接交付一个新价值”的能力。门店、效果和首次活动场景可在同轮交付真实结构素材，不再先问客户是否需要。
- 主动 SOP 已移除“最早阶段必须先发”“只能合并相邻阶段”“重复候选必须强制轻触”等代码语义约束；模型可以在合法、到期且未重复的候选中选择新价值。付款前置、频率、安全和结构保护仍保留。
- 固定开场白保持配置直发；`sop_platform_task` 保持平台消息类型、顺序、正文和 URL 原样转发。
- 当前候选可部署到 V2 sidecar 做 `sim_` 接口验证。主动 SOP 改动本轮不部署到 V1 worker，必须先做离线事件预览和人工审核。

## 架构与边界

V2 普通回复链路：

`Shared Context -> Gate / Tool Planner 并行 -> 只读工具 -> Evidence Join -> Reply -> 结构校验 -> 事实审计 -> Commit`

节点职责：

- Gate：最多提名 3 个真实内容资产及证据用途，不输出最终话术、工具参数或付款决定。
- Tool Planner：只规划门店、案例、订单和支付等只读查询，不接收话术正文和销售策略。
- Join：只合并聊天、候选、工具事实、缺失事实和权威冲突，不生成销售文案。
- Reply：唯一销售大脑，自主判断证明、降阻、推进、成交或暂停，并生成最终客户可见消息。
- Fact Auditor：只核验事实支持、时态、条件和承诺的结构交付，不评价销售力度，不生成话术。
- Commit：只在回复硬校验通过后执行允许的延后写操作。

代码继续硬校验：客户可见门店、真实素材、金额和人数、已付及风险禁卡、同轮一张卡、引用真实性、时间先后、Schema、幂等和非空回复。

代码不判断：客户心理、顾虑是否解决、是否必须回主线、门店后接什么、是否询问到店时间、软拒绝使用哪种理由。

## 本轮改动

### V2 销售节奏

- 增加“交付即完成一次铺垫”的高层原则：客户无需专门确认认可；没有继续质疑时，Reply 可切换到一个相关新价值。
- 新进展必须是历史未交付的事实、证据或可执行动作；复述旧价格、旧活动、旧门店和旧案例不算推进。
- 提问只用于获取会改变下一步的信息，禁止“能不能接受、是否方便、要不要继续”等许可式推进。
- 软拒绝和延后决定不自动等于暂停；工作、开车、现实事务、健康风险、投诉、强拒绝和停止联系才进入暂停边界。
- 完整内容资产被采用时，必须保留其核心事实、条件和结构素材。首次活动介绍必须包含当前活动核心事实与宣传图，不能混入预约金卡。
- 历史刚发送的案例图、活动图和门店卡可以用对话引用承接，不立即重复发送。

### 权威行动成本事实

以下事实作为 Reply 可选证据，不是固定模板：

- 整体过程约 45～50 分钟，仅指项目过程，不代表交通或等候时间。
- 做完不影响正常工作和生活，不扩展为绝对无感、无恢复期或任何人都无反应。
- 完成线上活动登记后，可以先到店了解和检测，确认适合、满意再操作；必须保留活动登记前提。

### 主动 SOP

- 候选顺序改为审计信息，不再强制选择最早未完成阶段。
- 模型可以从所有已到期、合法且历史未重复的新价值中选择一个目标。
- 夜间积压最多融合两个互补资产，并服务同一个客户目标。
- 付款候选仍要求更早活动事实、另一项真实价值和当前客户行动引用；代码只核验引用、角色和先后关系。
- 没有新价值时允许跳过，不通过换句话重复催促伪造触达。

## 验证结果

### 确定性回归

- `git diff --check`：通过。
- `python -m compileall -q ai_paths/app`：通过。
- `PYTHONPATH=ai_paths python -m pytest workflow_tests -q`：`1342 passed, 2 skipped`。
- Secret scan：未发现 API Key 或发送 Token 落盘。

### 低成本真实模型仿真

- 16 条 V2/SOP 多轮轨迹各运行 1 次：硬结构通过率 `100%`，基础设施失败 `0`。
- 覆盖门店、开场后推进、效果案例、健康风险、门店距离、首次活动、成熟付款、软拒绝、明确拒绝、工作暂停、已付时间不确定、SOP 沉默推进、重复避免、聊天中阻断和平台任务直转。
- 失败/高风险项定向复测：门店完整资产、效果事实审计、软拒绝和付款链路均无硬错误。
- 最新门店完整资产场景耗时约 `30.1s`；16 条样本 P50 约 `50.2s`、P90 约 `68.1s`。本阶段按计划只记录耗时，不作为失败门槛。

本轮模型仿真使用 `skip_review`，因此只能证明硬结构、事实来源和链路可运行，不能将其表述为“总体语义通过率达到 90%”。客户可见回复已做人工抽样，正式扩大真实流量前仍需在 V2 sidecar 使用隔离客户审核。

### Sidecar smoke 修复

- 首次部署后的 `sim_` 软拒绝 smoke 发现：Reply 首答正确选择了“整体约45～50分钟”作为新价值，但 Fact Auditor 的权威事实投影没有携带该新增字段，因而将其拦截；Repair 删除事实后退化成被动结束。
- 根因是 Reply 与 Fact Auditor 的事实输入不对称，不是销售判断规则不足。
- 已将 `service_duration / daily_life_impact / registered_visit_option / action_cost_fact_policy` 加入统一 `offer` 事实投影并增加合同测试；没有通过 Python 追加销售文案或关键词分流绕过审计。
- 固定开场白隔离 smoke 还发现：`test_isolated=true` 曾被运行时覆盖为可持久化，并在开场前查询真实平台订单；`sim_` 客户查询失败后错误降级到普通 Reply。现已使隔离请求保持 `memory_persist_allowed=false`，固定开场在隔离模式直接读取 `s10_new_customer_opening`，不查询平台订单、不写 SOP 任务。真实生产开场仍保留实时订单已付保护和 send-once 记录。

## V1/V2 隔离发布

- V1 继续使用 `/opt/ai-paths/shared/sop_reply_packs.json` 和生产 SOP worker。
- V2 使用独立 `/opt/ai-paths-refactor/shared/sop_reply_packs.json`，只为 V2 Reply 提供本次验证后的活动/案例资产。
- V2 sidecar 保持 `AI_PATHS_SERVICE_ROLE=reply_chain_refactor`、后台 worker 关闭。
- V2 与 V1 共用业务数据库、门店、订单和发送事实，但 `sim_` smoke 设置 `test_isolated=true`，不写助手消息、客户记忆、发送记录、SOP 任务或后台业务动作，也不为固定开场查询真实平台订单；为保证接口级审计，`sim_` 会话、入站消息和运行日志仍会写入共享运行数据库。
- 本轮不替换 V1 current、不重启 V1、不更新 V1 `/sop` 配置。

## 残余风险

- 主动 SOP 模型选择变化只完成确定性与离线仿真，没有在 V1 worker 上线；这是有意的发布隔离，不是遗漏。
- `sop_platform_task` 可能包含平台提供的赠品或其他营销事实，系统按协议原样转发；其事实责任属于平台任务输入，不能被模型擅自改写。
- V1 旧 Prompt 仍包含 `selected_scene_id` 等场景标签；V2 合同测试证明不可达。本轮不删除仍被 V1 使用的代码，避免影响生产链路。
- 模型仿真只有低成本单次覆盖和失败定向复测，尚未完成普通 3 次、关键 5 次的稳定性矩阵。
- V2 测试隔离仍会在共享运行数据库保存 `sim_` 请求日志；不会触达真实客户，但测试后应按 `sim_` 范围清理审计数据。

## 发布建议

1. 提交当前实验分支。
2. 只部署 V2 sidecar，并切换到 V2 私有 SOP 资产快照。
3. 用 `sim_` 客户验证首次活动、门店后推进、效果案例、软拒绝、成熟付款和暂停边界。
4. 确认 V1 current、V1 SOP 配置哈希和 V1 服务状态未变化。
5. 人工审核 V2 原话后，再决定是否把主动 SOP 改动迁移到最新 `main`。
